# Community Jobs - Product Overview

`community-jobs` is the Kora/Handles ecosystem's lightweight artifact repository for work that is useful to preserve, review, and share, but does not belong as canonical application code in a service repo.

In practice, that means this repository is the home for:

- community API query outputs
- small investigation or reporting artifacts
- public tracking notes that point to work happening in another repo
- helper scripts and tests when they make an artifact reproducible

This repository is intentionally not an application.
It does not run a service, own deployed infrastructure, or define the production behavior of the Handles ecosystem.
Its job is narrower and more operational: keep useful outputs from disappearing into shell history, transient executor sandboxes, or private support threads.

## Why this repo exists

K.O.R.A. and the broader Kora/Handles team frequently need to answer questions such as:

- "Can you export a list of handles that meet a condition?"
- "Can you capture the first page of the public API and summarize it?"
- "Can you leave a durable trail that links a community-facing request to the sibling repo that owns the code change?"
- "Can you preserve a short runbook or investigation note so the next responder does not start from zero?"

Those requests are too important to leave as ad hoc one-liners in chat, but they are often too small or too output-oriented to justify creating documentation in the owning service repository.
`community-jobs` provides that middle ground.

## What success looks like

This repo is working well when it gives teammates three things quickly:

1. Traceability: what was requested, what input or environment was used, and what output was produced?
2. Reproducibility: can another engineer or executor run the documented steps and validate the result?
3. Discoverability: can someone unfamiliar with the original request find the folder, read the README, and understand the artifact without tribal context?

The repo is not supposed to be clever.
It is supposed to be durable, boring, and easy to trust.

## Who uses it

The primary audiences are:

- Community and support staff who need a durable answer to a request such as an export or count.
- Engineers and on-call responders who need a safe public tracking artifact for work implemented elsewhere.
- AI executors that need a stable place to deposit reviewable outputs.
- Future maintainers who need to understand why a folder exists and whether it is still relevant.

Each of those audiences benefits from the same qualities: explicit provenance, copy-pastable steps, and outputs that are safe to keep in Git.

## What counts as a job

In this repo, a job is a bounded unit of work with:

- a clear request or reference
- explicit inputs
- documented steps
- one or more committed outputs
- at least one verification path

The typical storage model is one job folder per request or executor run.

Current examples already in the repository illustrate the range:

- `can-you-give-me-a-issue-1/` is a minimal export artifact that reads a snapshot from a sibling repo and writes a newline-delimited text file.
- `list-the-first-page-of-issue-27/` is a small Python-backed query artifact that hits `https://api.handle.me/handles`, saves a structured JSON output, and includes unit tests.
- `api-timeout-remediation-*` folders are legacy tracking or handoff artifacts associated with work owned by `api.handle.me`.

## Relationship to sibling repos

This repo frequently references other repositories, but that should not be confused with ownership.

Examples:

- Query artifacts may use snapshots generated by `api.handle.me` or another sibling checkout.
- A tracking artifact may summarize an issue, alert, or remediation that is actually implemented in `api.handle.me`, `handle.me`, or another repo.
- A helper script in this repo may describe or verify an output, but it should not become the system of record for a production workflow that belongs elsewhere.

The central rule is simple:

- outputs and tracking context can live here
- canonical behavior changes belong in the owning repo

That distinction is especially important because this repository already contains some legacy patch-style folders.
Those folders remain valuable as history, but they should not be treated as the preferred pattern for new work.

## In scope

- Small, reviewable exports such as `.txt`, `.json`, `.csv`, or concise markdown reports
- Job READMEs that explain request context, inputs, run steps, and verification
- Lightweight helper scripts and tests when they materially improve reproducibility
- Tracking notes that make cross-repo work understandable without copying the whole story
- Documentation that defines quality, safety, structure, and templates for contributors

## Out of scope

- Running services, daemons, schedulers, or queues
- Long-lived business logic that belongs in another repo
- Storing secrets, private keys, tokens, or raw sensitive logs
- Large binary artifacts, raw database dumps, or opaque blobs with no provenance
- Turning this repo into the default patch exchange for implementation changes in sibling repos

## Product principles

The product posture of this repo is defined by a few principles:

- Keep artifacts explainable.
- Prefer deterministic outputs over hand-waved summaries.
- Prefer small committed scripts over giant undocumented shell snippets when complexity rises.
- Prefer linking to canonical sources over copying large chunks of text or code from sibling repos.
- Prefer additive history over silent replacement when an artifact materially changes.

## How to navigate this repo

Use the docs in two passes:

- `docs/product/*` explains why the repo exists and what a good artifact looks like.
- `docs/spec/*` explains exactly how folders, READMEs, templates, and query artifacts should be structured.

Then move to the relevant job folder at repo root.
The folder README should tell you the original request, the inputs, the commands, the outputs, and the verification path.

If a folder cannot answer those basic questions, it is incomplete even if the output file exists.

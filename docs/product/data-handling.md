# Community Jobs - Data Handling and Safety

This repo stores outputs, notes, and supporting files that are meant to remain durable and reviewable in Git.
That sounds simple, but output-oriented repositories can become risky quickly if contributors treat every captured file as safe by default.

This document defines the data-handling posture for `community-jobs`.

## Core rule

If an artifact would be risky to expose to every reviewer with repo access, it probably does not belong here in raw form.
Prefer safe derived outputs and explicit reproduction steps over committing sensitive source material.

## Data categories

When deciding whether an artifact belongs in this repo, classify the data first.

### 1) Public chain data

Generally acceptable:

- handle names
- policy IDs
- transaction IDs
- UTxO references
- datum hashes
- other public on-chain identifiers

This category is the natural home for many community export jobs.

### 2) Derived aggregates

Usually acceptable:

- counts
- distributions
- summaries
- report tables derived from public or safely accessible data

Derived aggregates are often preferable to raw source material because they preserve the useful answer without preserving unnecessary detail.

### 3) Operational metadata

Case-by-case:

- status codes
- timeout values
- stack traces
- captured request parameters
- build or branch references

Operational metadata can be safe, but it requires review because it may accidentally expose internal details, secrets, or misleading partial context.

### 4) User-submitted or potentially identifying data

High caution:

- direct personal identifiers
- private communications
- copied ticket contents that were not intended for repo storage
- data that could become personally identifying when combined

This category should usually be summarized or redacted rather than committed verbatim.

### 5) Secrets and credentials

Never acceptable:

- API keys
- OAuth tokens
- JWTs
- cookies
- private keys
- seed phrases
- connection strings with credentials

No artifact value justifies committing these.

## Hard prohibitions

Never commit:

- private keys or seed phrases
- session cookies or signed requests
- access tokens of any kind
- raw production database dumps
- unredacted customer PII
- internal-only URLs containing embedded credentials
- executor stdout or stderr logs that may carry sensitive or noisy data, unless a reviewer has explicitly decided a redacted subset is safe and necessary

The repo currently contains older operational artifacts and legacy logs in history.
Treat those as historical exceptions, not as permission for new commits to follow the same pattern.

## Large output policy

Large artifacts create long-term maintenance cost.
Before committing a large file, ask:

- Is the full file genuinely needed?
- Could a deterministic generator command plus a smaller sample answer the same need?
- Could a structured summary be more useful than a raw dump?

If a large output is still the right answer, document:

- expected size or line count
- sorting rules
- the exact source snapshot or endpoint
- why storing the full artifact is justified

## Snapshot handling

Many community jobs should operate on snapshots generated by sibling repos rather than hitting live systems repeatedly.
When a snapshot is used:

- identify the snapshot path
- identify the owning repo
- describe how the snapshot was produced or where to learn that
- avoid copying the full snapshot into this repo unless the snapshot itself is the intended artifact and is safe to store

The `can-you-give-me-a-issue-1/` example follows this model by reading `../api.handle.me/tmp/handles_utxos.json` and committing only the derived text export.

## Live API query handling

Some jobs intentionally capture a live public API response.
When that happens:

- bound the request scope tightly
- document the exact endpoint and query parameters
- document headers that materially affect semantics
- document timing and freshness assumptions
- store the safe derived result, not noisy raw transport logs

The current `list-the-first-page-of-issue-27/` artifact is a good example of a bounded live capture:

- one endpoint
- explicit pagination parameters
- structured JSON output
- meaningful summary metadata
- tests for the parsing logic

## Redaction guidance

When you must include operational evidence:

- remove secrets entirely, not partially
- replace unstable or private identifiers with stable placeholders when practical
- summarize long logs instead of committing them raw
- review file paths, headers, and environment variable names for accidental leakage

A short human summary is often more useful than a giant raw excerpt.

## Reproducibility versus safety

Reproducibility matters, but it does not outrank safety.
If reproducing an artifact requires privileged access:

- document the safe steps to obtain the input
- document the command to run
- commit only the safe output or redacted summary

This gives future maintainers a real path to regenerate the artifact without turning the repo into a sensitive-data archive.

## Cross-repo content handling

This repo often points to sibling repos.
When referencing them:

- prefer linking over copying
- keep quoted code snippets minimal
- avoid turning a tracking artifact into a shadow copy of another repo's implementation details

The artifact should preserve what is necessary to understand the job, not rehost entire patches or long code excerpts by default.

## Safety review checklist

Before opening a PR, ask:

- Does every committed file belong in Git?
- Would I be comfortable with every repo reviewer seeing this file?
- Does the artifact preserve more raw data than is actually needed?
- Could the same value be achieved with a smaller or more redacted output?

If the answer is uncertain, reduce the artifact and strengthen the README rather than hoping review will catch it later.
